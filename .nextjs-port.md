# Next.js Port Plan (dormant until the user asks)

Trigger: the user says something like "make the Next.js version", "port this system to Next.js", or "add this content system to my Next.js site". Read HANDOFF.md and AGENTS.md first, then follow this plan.

## Goal

A Next.js twin of this starter where **agents publish exactly the same way**: same `src/content/` folders, same frontmatter, same AGENTS.md rules, same scripts, same `npm run check` gate, same free static hosting (Cloudflare Pages / Netlify). Only the rendering layer changes.

Two modes:
- **Mode A, new starter:** a separate repo `static-blog-starter-next` built from this plan.
- **Mode B, existing Next.js site** (for example the user's own portfolio): add the content layer + templates into their app without breaking existing pages. Inspect their repo first (router type, styling, hosting, existing blog) and report the plan before editing.

## Hard constraints

- `output: 'export'` (static HTML in `out/`), `trailingSlash: true`, `images: { unoptimized: true }`. Free hosts serve files only; no Node server.
- App Router, React Server Components by default. `'use client'` only for real interactivity (mobile menu, accordions if not using `<details>`). Keep shipped JS small; Core Web Vitals matter for these clients.
- Every dynamic route: `generateStaticParams()` + `export const dynamicParams = false`.
- No features that need a server: no middleware, ISR, API routes, Server Actions, `next/image` optimization, `headers()`/`cookies()`.
- Content format is frozen: never change frontmatter field names or folder layout. Agents and scripts depend on them.
- House rules still apply: no em dashes, white-label, City + ZIP formula, WCAG contrast.

## package.json scripts (target)

```
"dev": "node scripts/build-images.mjs && next dev",
"build": "node scripts/build-images.mjs && next build && pagefind --site out",
"qa": "QA_DIST=out node scripts/qa-site.mjs",
"check": "npm run lint:content && npm run build && npm run qa",
(all other scripts identical to the Astro starter)
```

Hosting: build command `npm run check`, output directory `out`, `NODE_VERSION=22`. Update `netlify.toml` (`publish = "out"`) and the Cloudflare deploy workflow (`pages deploy out`).

## Build order (Mode A)

1. `create-next-app` (TypeScript, App Router, no Tailwind, `src/` dir), set `next.config` constraints above.
2. Copy the carry-over items. Make the scripts' default output dir configurable where they reference `dist` (only `qa-site.mjs` does; it already reads `QA_DIST`).
3. Content loader + schemas; prove that an invalid entry fails `next build` with a readable message.
4. Image prebuild + `<ResponsiveImage>`.
5. Markdown pipeline + TOC.
6. Base layout, design layer, SEO metadata, JSON-LD, analytics.
7. Templates and routes in this order: blog post, blog archive + pagination + categories, case study, service, location, contact/thank-you/legal/about/search/404.
8. sitemap, robots, rss, llms.txt, IndexNow key file, Pagefind.
9. Port the sample content and run `npm run check`.

## Acceptance tests (must match the Astro starter)

- `npm run check`: 0 lint errors, 0 QA errors, on the sample content.
- Generate the stress set (282 posts, 12 drafts, 6 scheduled, 30 case studies, 15 services, 120 locations): build succeeds, QA 0 errors, drafts/scheduled absent from pages, sitemap, RSS, llms.txt.
- Invalid frontmatter fails the build. Stray `.mdx`/flat `.md` fails the lint.
- `</script>` in a FAQ answer does not break JSON-LD.
- Same URL structure with trailing slashes as the Astro site, so a client can switch frameworks without redirects.
- No horizontal overflow at 390 px on every page type. First-load JS on a blog post stays small (report the number from `next build`).
- Compare built HTML of one post, one service, one location against the Astro output: same title, meta, canonical, schema types, H1, internal links.

## Mode B notes (adding to an existing Next.js site)

- Detect App vs Pages Router; if Pages Router, use `getStaticPaths`/`getStaticProps` equivalents, same loader.
- If the site uses Tailwind or a component library, keep it for their pages and scope the template styles (the spec class names) to the content routes.
- If they deploy on Vercel with a server, `output: 'export'` is optional, but keep the same content layer so it can move to free static hosting later.
- Do not touch their existing routes; add content routes alongside. Check for URL clashes (`/blog`, `/services`) and agree on paths with the user first.
- Existing posts in another format (MDX, CMS): migrate them into `src/content/blog/<slug>/index.md` and add 301s.
